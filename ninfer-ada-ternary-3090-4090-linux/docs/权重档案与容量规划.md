# 权重档案与容量规划：`weights_id` 究竟改变了什么

三元制品声明 `identity.weights_id = "folded-ternary"`，groupwise 制品声明 `"groupwise-int"`。
这个字符串在引擎里唯一的作用，是让**本该返回 0 的容量查询不再返回 0**。它不参与任何一次矩阵乘，
也不改变任何一个算出来的数。

本文把这条结论拆成可核对的部分：概念分层、逐条查询对照、失效模式，以及四组配对实测。
文中每个论断都标注了来源是**源码**还是**实测**；两者都没有覆盖的地方列在 §7。

---

## 0. 结论摘要

| 命题 | 判定 | 依据 |
|---|---|---|
| 档案改变模型的数值输出 | **否** | 绑定层不读档案（§2）；改法落地前后两种三元制品的正控摘要 `9ab7f3dfe667` 与两个负控摘要逐位不变（§6.2）|
| 档案决定"用哪套权重" | **否**。权重由制品内容决定，档案只是**索引** | §2 |
| 档案改变各容量查询的返回值 | **是**：7 条查询按档分派，1 条不分派 | §3 |
| 档案改变**实测的工作区总容量** | **在已观测的 4 种配置下：否** —— 两档给出完全相同的值 | §6.1 |
| 身份写错会立刻失败 | **是**，且三个方向有三种不同症状 | §5 |

## 1. 三层不同的东西

容易混在一起的是三个层次，它们出现的时机与可见性完全不同。

| 层 | 载体 | 谁定义 | 何时可见 |
|---|---|---|---|
| **制品身份** | 容器 JSON 里的 `identity{model_id, weights_id}` | 打包器写入 | 读容器头部即可见，**在任何权重被读之前** |
| **权重档案** | 引擎枚举 `WeightsProfile` | 引擎由身份映射得到 | 规划期 |
| **张量格式** | 每个对象的 `NumericFormat`（运行期是 `QType`）| 制品对象表逐张量声明 | 绑定期 |

身份到档案的映射是全部逻辑所在（`src/targets/qwen3_6_27b/impl/package.cpp:85`）：

| `model_id` | `weights_id` | → 档案 |
|---|---|---|
| `qwen3.6-27b` | `groupwise-int` | `GroupwiseInt` |
| `qwen3.8-27b` | `groupwise-int` | `GroupwiseIntW8Endpoints` |
| `qwen3.8-27b` | `folded-ternary` | `FoldedTernary` |
| 其它任意组合 | | 抛 `std::runtime_error` |

常量定义在 `.../export/ninfer/targets/qwen3_6_27b/package.h:85-87`（`model_id`、
`qwen3_8_model_id`）与同文件第 39 行的枚举、`folded_weights_id`。

"模板是 `groupwise-int`、产物是 `folded-ternary`"因此不是自相矛盾：模板提供的是容器骨架与
未被三元覆盖的张量（`text/final_norm` 等），它的身份在打包时被**校验**；产物的身份被**改写**
（`tools/pack.py:80,490`）。

## 2. 绑定期不读档案

`bind_artifact()` 里三个档案走同一个 `case`（`.../impl/load/bindings.cpp:380-388`）：

```cpp
case WeightsProfile::GroupwiseInt:
case WeightsProfile::GroupwiseIntW8Endpoints:
case WeightsProfile::FoldedTernary:
    // 三档共用同一张文本层对象表：绑定层按对象名与制品声明的格式物化，从不看权重档案
    bind_groupwise_text_layers(binder, out);
    break;
```

唯一看起来像例外的是 `endpoint_format()`（同文件 :34-47）：`FoldedTernary` 返回
`NumericFormat::PTQ1_0_G128`。但该返回值**只用于选中"读制品声明"那条绑定路径**
（`is_row_split_grouped`），实际格式一律取自制品自己 —— 所以同一个档案能同时服务
PTQ1_0 与 PQ2_0 两种打包。

> 源码级结论：**档案不进入任何算子，也不进入权重物化。** 它只出现在容量查询里。

## 3. 七条按档分派的容量查询，与一条例外

四个档案里，`GroupwiseInt` 与 `GroupwiseIntW8Endpoints` 在所有这七条查询上取值相同，
所以下表按"groupwise（含 W8）"与"folded-ternary"两列给出。`R(k, t)` 记 §4 的旋转缓冲字节数。

| # | 查询（`variant.cpp` 行号）| groupwise（含 W8）| folded-ternary |
|---|---|---|---|
| 1 | `attention_projection_workspace_capacity_bytes` (:300) | `0`（融合路线把投影写进调用方张量）| `R(5120, last)` |
| 2 | `attention_output_projection_workspace_capacity_bytes` (:317) | `linear_add(Q5G64_F16S, …)` = `0` | `linear_add(PQ2_0_G128, …)` |
| 3 | `gdn_input_projection_workspace_capacity_bytes` (:336) | `0` | `R(5120, last)` |
| 4 | `gdn_input_projection_snapshot_workspace_capacity_bytes` (:352) | 上游 `…_snapshot_workspace_capacity_bytes` | `…_snapshot_folded_workspace_capacity_bytes` |
| 5 | `gdn_input_projection_record_workspace_capacity_bytes` (:371) | 上游 `…_record_workspace_capacity_bytes` = `0` | `…_record_folded_workspace_capacity_bytes` = `R(5120, B·width)` |
| 6 | `gdn_output_projection_workspace_capacity_bytes` (:391) | `linear_add(Q5G64_F16S, …)` = `0` | `linear_add(PQ2_0_G128, …)` |
| 7 | `post_mixer_workspace_capacity_bytes` (:422) | `gate_up = Q4G64_F16S`、`down = Q5G64_F16S` | `gate_up = PQ2_0_G128`、`down = PQ2_0_G128` |
| — | `gdn_norm_control_projection_workspace_capacity_bytes` (:412) | `gdn_norm_gating(48, 5120) + R(5120, last)` | **同左，逐字节相同** |

三个 groupwise 家族（Q4/Q5/Q6/W8）的 `linear_workspace_capacity_bytes()` **一律返回 0**
（`src/ops/linear/linear.cpp:118-137`）：融合路线把结果直接写进调用方张量，不需要中间 scratch。
三元不行 —— 矩阵乘之前必须先把激活映射进折叠基，那块 `[K, T]` 的 BF16 缓冲是硬需求
（同文件 :138-146）。

第 8 行那条例外值得单独说明：它的签名里**没有** `WeightsProfile` 参数。源码注释给的理由是
该查询被运行时模板与 35B 目标共用，而后者没有折叠三元档，所以保留无条件预留。对 groupwise 制品
这是**保守的多留**（方向安全），详见 §7。

## 4. 旋转缓冲的量

```cpp
// src/ops/linear/ternary/ternary_rotation.cpp:46
std::size_t ternary_rotation_workspace_bytes(std::int32_t k, std::int32_t tokens) {
    if (k <= 0 || tokens <= 0) { return 0; }
    return static_cast<std::size_t>(k) * static_cast<std::size_t>(tokens) *
           kActivationBytesPerElement;   // = 2，BF16
}
```

本 target 上折叠父权重的输入宽度恒为 `hidden = 5120`，于是 `R(5120, t) = 10240 · t` 字节：

| t | 1 | 128 | 512 | 1024 | 2048 |
|---|---|---|---|---|---|
| `R(5120, t)` | 10 KiB | 1.25 MiB | 5 MiB | 10 MiB | 20 MiB |

这是**单条查询**的量，不是总容量。总容量是各查询在工作区布局里取峰值的结果（§6.1 表明它由
某个与档案无关的查询决定）。

## 5. 失效模式

三个方向都有明确症状，且互不相同。

| 情形 | 机制 | 症状 | 检出手段 |
|---|---|---|---|
| 三元制品声明成 `groupwise-int`（改了 `pack.py` 之前的产物）| 旋转缓冲不被预留 | record 路径的**叶子竞技场**只剩 `kMinimumLeafWorkspaceBytes = 1` 字节，算子首次分配即越界，`DeviceArena::alloc_bytes` 抛 `std::bad_alloc`（`src/core/arena.cu`）| 端到端 / `--spec mtp`；**`ctest` 覆盖不到** |
| groupwise 制品按三元最坏情况预留（修复前的实现）| 白占临时字节 | `ninfer_gdn_input_proj_conv_{snapshot,record}_test` 的 `peak_used() == 查询值` 断言失败 | `ctest` |
| 身份组合不在表里 | `resolve_weights()` 直接抛错 | `artifact identity '…/…' is not supported by target '…'` | 装载即失败 |

"少留 → 崩"与"多留 → 断言失败"的不对称值得记住：**多留只会浪费，少留会让图构建中止**。
叶子竞技场那条路径尤其隐蔽 —— 它是从外层工作区**借来**的一段，容量等于外层为它预留的量，
全局竞技场再大也救不了它。

## 6. 实测

### 6.1 两档的工作区总容量

方法：同一台机器、同一个 `ninfer_bench` 二进制、同一语料，只换制品；命令行参数逐字相同。
取 CSV 的 `workspace_capacity_bytes` 列（引擎内存规划 `MemorySummary` 的字段）。

| 配置（`-r 1 --warmup 0`，bf16 KV）| `folded-ternary`（PQ2_0）| `groupwise-int`（官方模板）|
|---|---|---|
| `-p 512`，chunk 1024 | 90,476,544 | 90,476,544 |
| `-p 2048`，chunk 1024 | 180,953,088 | 180,953,088 |
| `-p 2048`，chunk 2048 | 361,906,176 | 361,906,176 |
| `-p 128,256,1024`（三者同轮）| 180,953,088 | 未测 |

读数：**三组配对配置下两档给出完全相同的总容量**，即档案分派没有改变任何一档的实测总容量。
（第四行为单档探测，只用于拟合下面的斜率。）

把同一批数字按"每 token 字节"整理，四组数据落在同一条直线上：

| `max_context` | chunk | 容量 | 容量 / min(ctx, chunk) |
|---|---|---|---|
| 512 | 1024 | 90,476,544 | 176,712 |
| 1024 | 1024 | 180,953,088 | 176,712 |
| 2048 | 1024 | 180,953,088 | 176,712 |
| 2048 | 2048 | 361,906,176 | 176,712 |

于是得到一个经验式（**观测归纳，非源码推导**）：

```
workspace_capacity_bytes ≈ 176,712 × min(max_context, prefill_chunk)
```

表中 `chunk = 2048` 那一行是这条式子的关键支撑：它的值**先按该式算出 361,906,176，随后实测一致**。
先有式、后有数，比事后复述读数更有判别力。

另外，`-p 128,256,1024` 同一轮里三个用例的容量完全相同，说明这个量取决于**规划的上下文容量**，
与实际 prompt 长度无关。

> **未做**：没有逐条分离各查询对峰值的贡献，因此"决定峰值的查询与档案无关"目前是**推论**
> （四组观测 + 那条不分派的查询对两档同值，与之相容），不是源码级证明。

### 6.2 数值不变

把实现从"无条件按三元最坏情况预留"改成"按档分派"前后，两个三元制品的端到端结果：

| 项 | 结果 |
|---|---|
| 5 条正控摘要 | `9ab7f3dfe667`，**逐位不变** |
| 负控摘要 | PQ2_0 `2c037e1df050`；PTQ1_0 `0e7f23175819`，逐位不变 |
| 制品字节数 | 10,533,732,876 B / 9,274,212,876 B，**完全相同** |

这三个数字合起来说明：改动只动了"留给多少临时字节"。

## 7. 未验证与边界

- **决定峰值的查询没有被识别出来。** §6.1 的斜率 176,712 B/token 未对应到任何单条查询；
  "峰值由与档案无关的查询决定"是三组配对观测支持的推论，不是证明。
- **第 8 条查询（`gdn_norm_control_projection`）对两档都多留**，且没有一个测试用例以该查询
  的名字直接覆盖它（`tests/` 下没有对应断言）。它是否曾经决定过峰值、多留了多少，本次没有分离。
- **容量只在 sm_89 + 单请求 + bf16 KV 下测过。** sm_86、`--max-concurrency > 4`、
  `int8`/`rk*` KV、batch > 1 下两档是否仍同值，未测。
- **`--spec mtp` 的叶子竞技场只有"修复前崩、修复后通"两个观测点**，没有记录它的容量数值。
- **经验式只由四点支撑，且都在本 target（qwen3.8-27B，hidden 5120）上取得。** 换模型或换
  `prefill_chunk` 上限后是否仍成立，未验证。
- 文中所有"源码"论断的行号取自打过本补丁的检出（对应 `patches/` 快照），不是上游原文行号。

## 8. 复现命令

```bash
# 两档配对比较（换制品，参数逐字相同）
for w in /data/Ternary-Bonsai-2-27B-ninfer/Ternary-Bonsai-2-27B-PQ2_0.ninfer \
         /data/Ternary-Bonsai-2-27B-ninfer/template/qwen3_8_27b.v2.ninfer; do
  /data/ninfer-build-bench/bench/ninfer_bench --weights "$w" \
    --corpus /root/ninfer-4090/bench/fixtures/bench_corpus.ids \
    -p 2048 --prefill-chunk 2048 -r 1 --warmup 0 -o csv | grep '^pp2048,'
done

# 数值不变（端到端一致性矩阵，需要 GPU 与真实制品）
just e2e /data/Ternary-Bonsai-2-27B-ninfer/Ternary-Bonsai-2-27B-PQ2_0.ninfer

# 逐条查询的源码对照
grep -n 'weights_profile' /root/ninfer-4090/src/targets/qwen3_6_27b/impl/variant.cpp
```

两档比较时**必须让 `-p` / `--prefill-chunk` / KV 类型完全一致**：容量随
`min(max_context, prefill_chunk)` 变化，拿不同参数的两次跑分对列，量的是配置差而不是档案差。
