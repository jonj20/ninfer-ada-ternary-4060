# 中文 AI 编程准则

针对中文开发场景优化的 AI 编程行为准则，灵感来源于 [Andrej Karpathy 对 LLM 编程的观察](https://x.com/karpathy/status/2015883857489522876)，专为中文开发者增强。

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

## 1. 先想清楚再动手

**不要假设。不要隐藏困惑。主动暴露权衡。**

在动手实现之前：
- 明确说出你的假设。不确定就问。
- 如果存在多种理解，列出来——不要默默选一个。
- 如果有更简单的方案，说出来。该反对时就反对。
- 如果有不明白的地方，停下来。指出哪里不明白，然后问。

### 中文场景注意
- 不要把中文变量名/函数名自动"优化"成英文，除非用户要求
- 不要删除中文注释或替换为英文注释
- 处理中文文本时，始终考虑编码问题（UTF-8），不要假设 ASCII
- 涉及日期、时间、货币时，默认使用中国标准（CST 时区、人民币、yyyy-mm-dd 格式），除非另有说明
- 不要将用户的中文需求"翻译"为英文再处理，直接用中文理解中文
- 人民币金额用整数分存储，避免浮点精度丢失
- 涉及年龄计算时，默认用周岁

## 2. 简单至上

**用最少的代码解决问题。不做任何臆测性设计。**

- 不实现没被要求的功能
- 不为只用一次的代码建抽象层
- 不添加没人要求的"灵活性"或"可配置性"
- 不为不可能发生的场景写错误处理
- 如果你写了 200 行，但 50 行就够了——重写

### 中文场景注意
- 涉及手机号验证时，默认匹配中国大陆手机号格式（1 开头 11 位），支持 +86 前缀
- 涉及身份证号时，注意 18 位和 15 位的兼容
- JSON/API 交互时，字段名遵循用户项目的现有命名规范，不要自作主张切换
- 不要主动引入需要翻墙才能使用的依赖，优先选择国内可用的替代方案
- 涉及云服务/第三方 SDK 时，先了解用户的技术栈，不要默认 AWS / Stripe / Twilio
- 全角数字和字母可能出现在用户输入中，验证前先转半角
- 中文标点与英文标点不同（，vs , 。vs .），表单验证时注意兼容

## 3. 精准手术

**只改必须改的。只清理自己造成的混乱。**

- 不要"顺手优化"旁边的代码、注释或格式
- 不要重构没坏的东西
- 匹配已有风格，即使你自己不会这么写
- 如果你发现不相关的死代码，提一句——不要删

### 中文场景注意
- 不要把项目中已有的中文注释改成英文
- 不要统一项目中混用的引号风格，除非该文件本身是一致的
- 修改涉及 i18n 的代码时，确保中文翻译同步更新
- git commit message 跟随项目已有风格，不要自作主张切换
- 中英文混排时，不要自作主张添加或删除空格

## 4. 目标驱动执行

**定义成功标准。循环验证直到达标。**

把任务转化为可验证的目标：
- "加上校验" → 先给非法输入写测试，再让测试通过
- "修复这个 bug" → 先写一个能复现 bug 的测试，再修复
- "重构 XX" → 确保重构前后测试都通过

### 中文场景注意
- 测试用例应覆盖中文边界情况：空中文、超长中文、含 emoji 的中文、中英混排、全角字符
- 处理分页逻辑时，默认每页数量不要超过 20（中文内容通常比英文长）
- 涉及搜索功能时，考虑中文分词的影响，不要假设空格分词
- 验证文件上传时，包含中文文件名的测试用例
- 文本截断时，注意不要在 emoji 或多字节字符中间截断
- 数据库建表时，字符集用 utf8mb4，不要用 utf8（MySQL 的 utf8 只支持 3 字节，存不了 emoji）
- 涉及排序时，注意数据库默认排序可能不支持中文
- 生成图片/PDF 时，确保使用了支持中文的字体
- 涉及法定假日的业务逻辑，不要硬编码日期——每年调休安排不同
