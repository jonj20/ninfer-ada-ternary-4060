设置长上下文直接失败，问题很可能不在 `NINFER_HOST_PAGEABLE` 这个变量上。这个变量只决定 HostKV 用哪种内存，不负责扩容 KV 容量。长上下文失败通常是 **KV 容量配置**或**启动参数**的问题。

### 核心原因：KV 容量不足或配置冲突

长上下文（如 262K）需要 KV 池有足够容量。如果 `--kv-capacity` 给得太小，或者用了显存占用过高的 KV 精度，启动时直接 OOM 或推理时失败。

### 按优先级调整配置

**1. 检查并调大 `--kv-capacity`**
`--kv-capacity` 是 KV 池的 token 容量上限，必须 ≥ `--max-context`。如果之前只设了 65536，要 262K 就会失败。
```bash
--max-context 262144 --kv-capacity 262144
```
或者用 `--kv-capacity auto` 让引擎按剩余显存自动计算。

**2. 降低 KV 量化精度（最关键的显存优化）**
默认的 `bf16` KV 在 262K 下占显存极大。必须换用更省显存的格式：
*   **推荐：`--kv-dtype int8`**，显存占用约为 bf16 的一半。
*   **更激进：`--kv-dtype fp8` 或 `k8v4`**，适合显存更紧张的场景。
*   **社区实测可用：`rk4v4-e8`**，有用户反馈在 32G 卡上 `fp8` 反而池子更小，换用此格式后池子增大 90%。

**3. 确保 HostKV 真正参与溢出**
`--host-kv-mib` 要设一个非零值，HostKV 才能在显存 KV 池满时接管溢出的 KV 数据。有用户设 `--host-kv-mib 24576`（24GB）实测有效。
```bash
--host-kv-mib 24576
```

**4. 显式指定 HostKV 为普通内存（如果之前设了锁页内存导致 OOM）**
如果你已经设了 `NINFER_HOST_PAGEABLE=1`，那这部分内存就不再计入显存了。如果还没设，且启动时报显存不足，可以加上这个环境变量。

### 参考启动参数（单卡 48G 跑 262K 的实例）

以下是社区里在 48G 卡上跑通 262K 的实际参数，你可以根据自己卡的大小等比调整：
```bash
--max-context 262144 \
--kv-capacity auto \
--kv-dtype fp8 \
--host-kv-mib 24576 \
--max-concurrency 3 \
--prefill-chunk 1024 \
--spec mtp --draft-tokens 3 --lm-head-draft
```
注意 `--prefill-chunk` 不要超过 1024，有用户实测 1665 会导致协作启动越界、GPU 卡死。

**KVMem 并非 llama.cpp 的官方内置分支，而是一个第三方实验性 Fork（通常指 `kvmem/kvmem-llama.cpp`）。** 它的核心逻辑是将 KV Cache 视为可检索的工作记忆：将过期的历史 KV 块（Block）卸载到主机内存（RAM）甚至磁盘（NVMe），仅在 GPU 显存中保留一个被检索到的“工作集”加上最近的 token，从而让消费级显卡（如 16GB）能够运行原本显存无法容纳的超长上下文（如 256K）。

### 核心机制：KV Cache 的“检索式卸载”

传统的推理方式要求整个上下文的 KV Cache 必须常驻显存。KVMem 打破了这一限制，其工作流程如下：

1.  **分块与卸载**：将过去的对话历史按固定大小的 **Block**（默认 **128 tokens**）进行切分。当对话历史超出显存预算时，被挤出窗口的 Block 会被暂存到主机内存中。
2.  **检索与重载**：当产生新的用户查询（User Query）时，系统会对存储在 RAM 中的历史 Block 进行评分。最相关的 Block 会被重新检索回 GPU 显存参与注意力计算。
3.  **硬件解耦**：这使得有限的显存只需负担模型权重、激活值以及**当前活跃的检索窗口**。实测表明，配合 KV 量化（如 Q8/Q4），16GB 显存的 RTX 5060 Ti 能够在运行 27B 模型时将上下文扩展至 **256K**，代价是占用约 **13-14GB 的系统内存**。

### 关键参数与配置逻辑

KVMem 通过一系列特有的启动参数来控制显存预算与内存层级：

| 参数 | 功能与逻辑 |
| --- | --- |
| `--kvmem-budget` | **显存 KV 硬预算**。设定该值后，历史 token 会被分块并仅在需要时换入换出。 |
| `--kvmem-gen-reserve` | **生成预留**。为即将生成的新 token 预留的显存槽位，**单次生成的长度不能超过此限制**（包含思考过程）。 |
| `--kvmem-conversations` | **多会话保留**。允许服务器在主机内存或磁盘中同时保留多个独立的对话状态（默认 1）。设为 >1 时，切换对话无需重新处理历史。 |
| `--kvmem-session-ram-gb` | **会话内存软上限**。当活跃与非活跃会话的 RAM 占用超限时，非活跃会话按 LRU 策略移至 NVMe 磁盘或直接丢弃。 |
| `--kvmem-session-nvme-gb` | **磁盘缓存配额**。启用后，RAM 压力会将非活跃会话溢出到磁盘，适合内存有限但 SSD 空闲的场景。 |

### 默认行为与使用模式

KVMem 默认**开启检索功能**，无需额外参数即可工作。其默认检索策略为 **128-token 块**，且采用 `query replay auto` 和 `user` 查询策略。

在使用时，客户端必须**每轮发送完整的历史消息（messages）**。KVMem 通过比对历史消息来识别是延续之前的对话（命中缓存）还是开启新对话（缓存未命中）。

### 实测效果与代价

根据社区及独立测试者的反馈，KVMem 展现出了显著的“显存换内存”特征：
- **优势**：打破了“显存容量决定上下文长度”的铁律。有用户报告在 12G/16G 显存上成功跑通 256K 上下文，速度维持在 **30-40 tok/s** 甚至更高（视模型与量化精度而定）。
- **代价与稳定性**：这种激进的内存换存策略并非没有副作用。有测试者指出，在超长上下文（如 186K）时可能存在**记忆遗忘或逻辑退化**（“总是犯错重试”）。其性能对系统内存带宽和 NVMe 读写速度较为敏感，且相比官方主线的优化，该分支的维护活跃度与兼容性存在不确定性。

**总结**：KVMem 本质上是为“显存受限但内存充裕”的本地部署场景设计的**分层缓存策略**。它通过牺牲部分系统内存和潜在的推理延迟，换取了在消费级硬件上运行超长上下文的可行性。
