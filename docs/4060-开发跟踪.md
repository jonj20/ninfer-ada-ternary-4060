# RTX 4060 8G · Ternary Bonsai 2 PTQ1_0 · Linux 移植开发跟踪

> 本文档跟踪 **RTX 4060（8 GiB，sm_89）** 上跑通 **Ternary Bonsai 2 27B · PTQ1_0** 的开发过程。
> 主线工程：本仓 `ninfer-ada-ternary-3090-4090-linux`。
> 状态字段用：`未开始` / `进行中` / `阻塞` / `完成` / `延期`。阶段完成后回写日期与证据。

---

## 0. 决策摘要（2026-09-23 确认）

| 决策项 | 结论 |
|---|---|
| 主线分支 | **`ninfer-ada-ternary-3090-4090-linux`**（本仓） |
| 目标硬件 | NVIDIA **RTX 4060 8 GiB**，**sm_89**，运行环境 **Linux** |
| 目标格式 | **PTQ1_0**（`PTQ1_0_G128` / `weights_id=folded-ternary`） |
| MTP / vision | **本期不支持**（对象表裁剪，不做联调） |
| 芯片支持 | **允许新增 4060 档位**（构建命名、容量档、文档与 bench 口径） |
| 独立 4060 引擎树 | **不建**。构建/产物用路径与环境变量区分；不与 Ambolio/4070 血统混树 |
| 4070 内核深优化 | **二期**按函数回移 + e2e 回归，不阻塞本期 |

### 为何选本线（对比后放弃的路径）

| 候选 | 结论 | 理由 |
|---|---|---|
| **3090-4090-linux（本仓）** | ✅ 主线 | 唯一完整 Linux 产品线（`just`/`uv`/补丁/转换/e2e）；**PTQ1_0 已 E2E**（391、MMA 双路径、负控）；`pack.py` 已参数化且校验 v2 模板 |
| ninfer-ada-ternary（主线文档包） | ❌ 不用作构建线 | Windows/4080S 血统，路径写死，无一键 Linux 构建 |
| ninfer-ada-ternary-4070-linux | ❌ 二期 | 内核优化最深，但是 Ambolio 补丁快照、无构建体系；与本线基线不同，合树成本高 |
| ninfer-ada-ternary-3090 | ❌ 不用 | bench/研究线，非发行线 |
| ninfer-ada-ternary-4060（Ambolio 拷贝） | ❌ 已删除 | 用户已删；避免双基线 |

**架构说明：** 上游本线仅注册 sm_86 / sm_89。4060 为 sm_89，**无需放宽架构白名单**，`just build`（默认 89）即可。

### P4 4060 8G 正确性冒烟 — 状态：`完成`（2026-09-23）

参考本线 `tools/verify/e2e_ternary.sh` 与移植报告 §4.7：

| 用例 | 期望 | 结果 |
|---|---|---|
| 贪心 `17 * 23` | **391** | **✅ 391** |
| `NINFER_TERNARY_MMA=1` vs `=0` | token 序列逐字节一致 | **✅ hash `b327e287e849`（c128/c1024 × mma1/0 四例全一致）** |
| `NINFER_TERNARY_HADAMARD=0` | 乱码（负控分离） | **✅ hash `b0decbd6b552` ≠ 正控** |
| 装载显存 | 权重+workspace+KV+ctx **≤ 约 7.5 GiB**（8G 卡） | **✅ 权重 5.52 GiB / 5.52 GiB，峰值见 §6.4** |
| 无 vision/mtp 引用错误 | 不因缺对象启动失败 | **✅（保留 mtp+vision 后正常装载）** |

> **制品绑定结论（R1 实测）：** 引擎绑定层把 mtp/vision 当**必选存在项**——`features.mtp()/vision()` 只决定 Device vs ValidateOnly，两者都要求对象存在；唯一真正可选的是 dflash2（`binder.has_object("dflash2/feature_projection")` 才 bind）。所以 text-only 制品必须**保留 mtp + vision，可裁 dflash2**。8G 起跑：text+mtp+vision 6.56 GiB + KV/workspace ≈ 7.0 GiB 仍放得下。
>
> **MTP 投机实测（Out 范围确认）：** `--spec mtp` 在 2048 ctx 下 `requested 924MB runtime but only 702MB available`——8G 卡本期不支持投机，与 §2 Out 一致。

```bash
  --prompt "What is 17 * 23? Answer with just the number." \

```

## 7. 专题：RTX 4060 与 4090 代码层兼容性

> 结论先行：**同一 sm_89 二进制路径，代码层兼容面一致**；差异在显存容量、SM/带宽与调优数字，不在「4060 不支持」。

### 7.1 架构与编译

| 项 | RTX 4060 8G | RTX 4090 24G |
|---|---|---|
| Compute Capability | **sm_89** | **sm_89** |
| 根 `CMakeLists` 白名单 | 允许 `86\|89` | 同 |
| 编译宏 | `NINFER_SM89=1` | 同 |
| 三元 / 通用 CUDA 内核 | **同一套 cubin** | 同 |
| 上游架构扩展 | 无需放宽（本就含 89） | 同 |

4060 与 4090 **同为 Ada sm_89**：编译目标、指令集、内核模板完全相同，不存在「4090 专属 kernel」或 4060 缺指令的分叉。

### 7.2 真实差异维度

| 维度 | 4060 8G | 4090 24G | 性质 |
|---|---|---|---|
| 显存 | **8 GB** | 24 GB | **硬约束**：全量 PTQ1_0 ~8.6 GiB 装不下；须 text-only + 收紧 ctx/KV |
| SM 数 | 24 | 128 | **性能**（占用/并行） |
| 显存带宽 | ~272 GB/s | ~1008 GB/s | **性能** |
| 默认容量档 | 必须收紧 | 可开很大 | **配置**，非架构 bug |
| WDDM / DirectStorage | Linux 下 `#ifdef _WIN32` 不走 | 同（Windows 才有） | 平台差异，与卡型号无关 |
| 内核注释里的调优数字 | 按大卡（如 66 SM）标定 | 主测卡 | **手感/性能**，带边界检查，功能仍正确 |

### 7.3 不在「4060/4090 互比」范围内的不兼容

- **sm_86（3090）**：另一档宏 `NINFER_SM86`，本仓以 89 为主。  
- **sm_120（5090 等）**：白名单拒绝。  
- **Windows-only** 特性（WDDM 预算、DirectStorage）：Linux 构建编不到，与 4060/4090 无关。

### 7.4 判定

| 问题 | 答案 |
|---|---|
| 4090 代码层是否完全兼容？ | **是**（本线主测卡，文档/bench 按它写）。 |
| 4060 代码层是否兼容？ | **是（同一 sm_89 路径）**；风险在 **8G 显存预算 + 未在真机冒烟（P4）**，不在 ISA/架构。 |
| 差异是否只是性能？ | **主体是性能与显存配置**；另加「按大卡标定的启动参数默认值」需 4060 收紧。 |

## 8. 专题：Bonsai 2 PQ2_0 vs PTQ1_0

> 结论先行：两种格式**并列支持、正确性都有 E2E**；PTQ1_0 **更省显存、解码更慢**，且**吃不满**当前为 PQ2_0 做的 GEMV/MMA 快路径。本期主力 PTQ1_0 是对的（8G），需接受速度并完成 P4。

### 8.1 格式与存储

| | **PQ2_0** | **PTQ1_0** |
|---|---|---|
| 码 | 2-bit 槽，4 码/字节 | **base-3 三值**，5 码/字节 |
| 每组 128 权重 | base **32 B** + scale 2 B = **34 B** | base **24 B** + high **2 B** + scale 2 B = **28 B** |
| 高位平面 | **无** | **有**（`qh`，权 120..127） |
| 解码 | 移位取码 `(c-1)*d` | **除/取模**，stages `{32,16,8}` |
| 权重例（`[248320,5120]`） | 337,715,200 B | **278,118,400 B（约省 17%）** |
| 业界 bpw | ~**2.125** | ~**1.75**（更省） |

引擎内是**两套独立 `decode_one`**（`ternary_rowsplit_storage.cuh`）；row 几何按 `qtype` 分派（`ternary_row_view.h`：PTQ1=24+2，PQ2=32+0）。**不是同一套码。**

### 8.2 体积与性能（4090，移植报告）

| | PQ2_0 | PTQ1_0 |
|---|---|---|
| 全量制品 | 9.810 GiB | **8.637 GiB** |
| 权重 | 6.70 GiB | **5.52 GiB** |
| decode | **52.3 tok/s** | **15.8 tok/s（约慢 3.3×）** |
| 慢因 | — | base-3 除模 + 高位平面（报告判「符合预期」） |

### 8.3 内核路径差异（为何 PTQ1 更慢不止解码）

| 路径 | PQ2_0 | PTQ1_0 |
|---|---|---|
| T=1 专用 GEMV | **有**（`ternary_pq2_gemv`；`qhigh==nullptr` 才准入） | 走**通用** reference 路径（有 `qhigh`） |
| small-T MMA（T=2..8） | **有**（`mma_admits` 仅 PQ2_0） | **无** → 通用 tile |
| 折叠 Hadamard 旋转 | 同 | 同 |
| `folded-ternary` 身份/容量档 | 同 | 同 |

`ternary_rowsplit_gemm.cu` 明确：GEMV 快路径与 small-T MMA 的准入条件含 `qtype == PQ2_0_G128 && qhigh == nullptr`。

### 8.4 正确性验证 —— PTQ1_0 **不是**「没验过」

| 检查 | PQ2_0 | PTQ1_0 | 出处 |
|---|---|---|---|
| `17*23` → **391** | ✅ | ✅ | 移植报告 §4.7 |
| MMA=1/0 正控摘要 | `9ab7f3dfe667` | **同一摘要** | §4.7 / §一致性 |
| `HADAMARD=0` 负控 | `2c037e1df050` | `0e7f23175819` | 分离即正确 |
| pack `check` | 原生 | **本仓已修几何/分片后 OK** | P1 |
| MTP 接受率（有投机时） | 76.9% | 74.4% | 报告回归段 |

**「文档多写 PQ2_0」的原因：** `just from-scratch`、bench 默认、部分 KV 矩阵举例用 PQ2_0（更快）；**正控摘要两种格式相同**（模型数学一致），负控不同（解码路径不同）——同一套 e2e 判据两边都成立。PTQ1_0 的解码正确性、旋转负控、尺寸反验在移植报告中均有行。

### 8.5 对「主力 PTQ1_0 + 4060 8G」的含义

| 维度 | 结论 |
|---|---|
| 正确性 | 已有 E2E/负控/pack check；**可用** |
| 8G 适配 | PTQ1_0 **更合适**（权重 5.52 vs 6.70；text-only 约 5.87 GiB） |
| 速度 | 明确更慢；4060 预期低于 4090 的 15.8 tok/s |
| 快路径 | 当前 PTQ1_0 **无** PQ2_0 专用 GEMV/MMA → 二期可选优化 |
| 风险 | **R7** 已登记：接受 base-3 慢；**P4 真机冒烟**仍是门槛 |

### 8.6 一句话

PTQ1_0 与 PQ2_0 是**并列支持的两套格式**，正确性**两边都验过**（同一正控摘要）；差异是 **更省显存、解码约慢 3×、且暂无 PQ2_0 快路径**。4060 主力用 PTQ1_0 合理，先完成 P4，速度接受基线或二期补 PTQ1_0 快路径。

### 9.1 优化跟踪：PTQ1_0 decode 效能（2026-09-23 立案）

> **待办事项，不属于本期 P0–P6 验收范围；作为二期优先项。**

**结论（暂行）：**
- 同机 4060、**同一 PTQ1_0 GGUF 文件**：llama.cpp **25 t/s** vs ninfer **3.36 tok/s**（稳态），差距 ≈ **×7.4**。
- 判定：ninfer 未有效发挥该格式硬件效能；主要嫌疑为 **PTQ1_0 base-3 除模 slow path**（与 PQ2_0 为两套 `decode_one`，PTQ1_0 无 GEMV/MMA 快指令）。

**进展（2026-09-24，一期落地）：PTQ1_0 SIMD 4-trit 解码 warp-per-row GEMV 快路径**
- 实现：`ternary_rowsplit_gemv.cuh` `ternary_ptq1_gemv_kernel<1>`——仿 llama.cpp `vec_dot_ptq1_0_q8_1_multi` 的 `__byte_perm`/`pow3`/`__vsub4` 单发 SIMD 解码，权重值与 reference `decode_one` 逐位一致（36 regs / 0 spill / 0 barrier）；`launch_ternary_gemm_t1` 分派，开箱默认启用，`NINFER_TERNARY_PTQ1_GEMV=0` 回退 reference 作 A/B（graph 稳定，静态读取一次）。
- 实测（4060 8G，同 prompt 同参 `--max-new 192 --kv-dtype rk4v4-e8 --greedy`）：decode **3.36 → 8.33 tok/s（×2.5）**；`NINFER_TERNARY_PTQ1_GEMV=0` = 3.37 tok/s 对上基线；391 正控通过，两次运行一致。对照 llama.cpp 25 t/s 差距 **×7.4 → ×3.0**。

**进展（2026-09-25，二期落地）：瓶颈定位 + tail 拆分 + int8 激活 `dp4a` 点积**

*一、根因定位（全部为 sm_89 微基准实测，非推断）*

| 测量 | 结果 |
|---|---|
| 该卡在 WSL 下的**可达带宽**（`tools/hbm_bandwidth_probe.cu`，常驻网格 uint4 纯读） | **249.6 GB/s** |
| 只读权重（code+scale），不碰激活 | **223–230 GB/s** |
| 只读激活 | 270–290 GB/s |
| 一期内核（两者都读） | **47 GB/s** |
| 同 load 量、但激活**不进 FMA 依赖链** | **146.6 GB/s** |
| 同结构、去掉 8 列 tail 解码 | 109.9 GB/s |

结论：**既不是访存模式、也不是布局或 WSL，而是指令发射率**。一期内核约 30 条指令处理 28 字节权重，实测 2.24 指令/cycle（发射上限 4）⇒ 指令受限。llama.cpp 每权重只花 1 条 `dp4a`（4 个 int8 乘加打包），指令密度差约 2.5×。另发现 128 列里 8 列（high 平面）单独付 **45%** 代价。

*二、三项改动*

| # | 改动 | 文件 | 内核效果（gate_up 39 MB） |
|---|---|---|---|
| 1 | group 循环 `#pragma unroll 8`；4 个 bf16 激活合并为单条 `LDG.64`；**8 列 tail 移出热循环**（lane `l` 领 tail 列 `l&7`、组 `l>>3` 步进 4，warp reduce 自然求和）；前后景用独立累加器避免依赖链串行 | `ternary_rowsplit_gemv.cuh` | 57 → **98 GB/s** |
| 2 | **int8 激活 + `__dp4a` 整数点积**（对齐 llama.cpp mmvq 的 q8_1 做法）：新增 `ternary_ptq1_quantize_act_kernel`（按 128 列组量化，warp 内归约无 barrier）+ `ternary_ptq1_gemv_dp4a_kernel`；scratch 为进程生命周期 device buffer，**CUDA graph capture 中不分配**并自动回退 bf16 | `ternary_rowsplit_gemv.cuh`、`ternary_rowsplit_gemm.cu` | 98 → **113–136 GB/s** |
| 3 | tail pass 改为**每个 lane 领整组**、一次 16B 装载取回该组全部 8 个 tail 激活（load 数从每 lane 30 次降到每 warp 3 次/组），并加 `#pragma unroll 8` | `ternary_rowsplit_gemv.cuh` | 136 → **162 GB/s**；312 MB 冷载荷 115 → **135 GB/s** |

端到端：**8.33 → 15.3 → 17.6 tok/s**。

开关：`NINFER_TERNARY_PTQ1_DP4A=0` 回退 bf16 激活路径（13.2 tok/s）；`NINFER_TERNARY_PTQ1_GEMV=0` 回退 reference（3.36 tok/s）。

*三、三期改动：借鉴 llama.cpp 的三进制递推（重排 lane→列映射）*

二期留下的结论是「要追上需要换 lane→列 的映射、让一次解码产出更多权重」。读 llama.cpp-prism 源码
（`ggml/src/ggml-cuda/vecdotq.cuh` 的 `vec_dot_ptq1_0_q8_1`，**该 fork 的 CUDA 后端确实有 PTQ1_0 的
vec_dot**，所以两边格式相同、差距全部来自内核结构）后确认了具体做法：它用

    v = (v * 3) & 0x00FF00FF

**原地递推**取 trit，一次 `__byte_perm` 拓宽的代价被同一 span 的 5 个 trit 摊薄；而二期把 pow3 当作
每 lane 常量、每 lane 只取一个 trit，等于每 4 个权重就要付一次拓宽。

新增 `ternary_ptq1_gemv_recurrence_kernel<kUnroll>`（`ternary_rowsplit_gemv.cuh`）：每 lane 领一个
4 字节 span 并一次吃完它的 5 个 trit（20 个权重），5 次 `dp4a` 先累进同一个 int32，最后只做一次
scale 乘法。一组共 6 个 span（前区 4 个覆盖列 0..79、中区 2 个覆盖 80..119），一次迭代推进 5 组 =
30 个 lane 参与，剩余 2 个 lane 复用第 29 号 lane 的 span 并用掩码清零贡献——这样把体内所有条件判断
移到循环之外（体内分支会退化成 BSSY/BSYNC，代价约 2 倍）。qh 的 8 列仍走独立 tail pass。
递推第 t 步发出的是 `((a·3^t mod 256)·3)>>8`，与原来的 `pow3=3^t` 形式**逐位相同**。

| 形状 | 二期 dp4a | 三期递推 | 提升 |
|---|---|---|---|
| MLP gate_up（N=34816, K=5120，真实） | 89.6 GB/s | **129.4 GB/s** | ×1.44 |
| MLP down（N=5120, K=17408，真实） | 133.2 GB/s | **168.1 GB/s** | ×1.26 |
| attn/GDN（N=5120, K=5120，真实） | 129.3 GB/s | **152.4 GB/s** | ×1.18 |
| 312 MB 冷载荷 | 96.7 GB/s | **137.5 GB/s** | ×1.42 |

40 寄存器、无溢出。unroll 按剩余迭代次数分档（≥4 用 4、≥2 用 2、否则 1）：K=5120（40 组）用 4 比用 2
再快约 3%，K=1536（12 组）用 4 反而回落。

端到端 decode **17.6 → 22.6 tok/s**（22.60 / 22.63，两轮交替运行抵消频率漂移），300 token 长生成
**23.02 tok/s**。新增开关 `NINFER_TERNARY_PTQ1_RECURRENCE=0` 回退 dp4a 内核（17.0 tok/s）。

*四、正确性与精度验证*

| 项 | 结果 |
|---|---|
| CPU 参考实现对拍（`tools/verify/ternary_gemv/gemv_reference_check.cu`，5 个形状含 N=257 奇数行 / K=1280 / K=3840） | max_rel_err ≤ **0.0038**（bf16 舍入量级），全部 PASS |
| int8 路径 vs bf16 路径（随机数据，4096×5120 / 2048×17408） | 每行相对误差中位数 **1.3%**、p90 5.6–6.7%；**RMS 比值 0.991**。p99/max 爆炸出现在真值近零的行（抵消，绝对误差极小） |
| 300 token 长生成（天空/海水为什么是蓝色） | 物理事实准确、无退化 |
| 数学题质询 | 素数判定与 √n 推理正确 |
| prefill 未回归 | 612 token prompt：prefill 11.16 / decode 16.75 tok/s |
| 三期递推内核 vs 二期 dp4a 内核（同一 int8 激活与权重，K=5120 / 1536 / **17408**，含余数组路径） | **逐位一致，0 元素差异**（K=17408 = 136 组 = 27 次迭代 + 1 组余数） |
| 三期 300 token 长生成（三值量化原理/优势/局限） | 23.02 tok/s，结构与公式正确、无退化 |
| greedy 文本在两个内核间有末位差异 | lane 归约分组改变 ⇒ 部分和相加顺序改变 ⇒ logits 末位翻转（近似打平处选到另一侧）。与 int8 激活同类，**不是解码错误**：两路输出语义等价，孤立对比逐位一致 |

*五、剩余差距的归属（`tools/verify/ternary_gemv/pattern_attribution.cu`，312 MB 冷载荷）*

每层只加一样工作、消费者保持极简，测的是访存模式本身：

| 访存模式 | 带宽 | 相对损失 |
|---|---|---|
| uint4 连续 | ~249 GB/s | — |
| 仅 code plane | ~249 GB/s | — |
| + activation 读 | ~249 GB/s | **激活免费**（常驻缓存） |
| + high / scale 两条侧流 | ~196–200 GB/s | **−22%** |
| + base-3 解码 | ~167–169 GB/s | −14% |
| + dp4a 与 scale 累加（= 真实内循环） | ~117–120 GB/s | −29% |

**重要修正：那 22% 不是「三平面布局」的代价，而是「多两条 load」的代价。** 把 28 字节重排成一条连续
交错块（模拟重打包、不改制品）实测与三平面**持平或更慢**（312 MB 载荷：154 vs 130、126 vs 124，
在 ±20% 噪声内）——因为交错后每组仍是 3 条 load，只是换了基址。**所以重打包权重布局这条路已否证。**

剩下的差距是**每权重的指令密度**，这条路已在三期兑现（递推解码，见上）：端到端 17.6 → 22.6 tok/s，
与 llama.cpp 22–28 t/s 的下沿持平。若要再往上，下一个结构性方向是**线程组织**——llama.cpp 的 PTQ1_0
MMVQ 是 CTA 内 4 warp 分工同一输出行的 K 维（每线程一整个 128 列块），再经 `tmp_shared` 归约一次，
每权重约 1.83 条整数指令；我们现在是 warp-per-row、每线程 20 列，约 2.3 条。

*六、四期：批量 prefill 内核（prefill 10.9 → 125 tok/s）*

四期起因是"用 WebUI 聊天不太行"。正式测试里 prefill 吞吐**与 prompt 长度无关、恒定 10.9 tok/s**
（401 / 781 / 1541 token 全是 10.9），这是"逐 token 串行"的特征。nsys 抓一次 302 token 的预填充：
**98.7% 的时间在参考分块 GEMM `ternary_rowsplit_gemm_kernel` 上**，而二/三期那套 int8 `dp4a` 优化
只接了 T == 1，预填充一点没吃到。

根因是那个参考 kernel 的形状：每 CTA 只做一个输出行（`grid = (rows, ceil(T/8))`），于是激活向量被
重复读 rows 次——gate_up 形状每层约 108 GB 的 L2 流量。折算下来 302 token × 27B 参数 = 1.63e13 FLOP
花了 28.1 s，即 **0.58 TFLOPS，只有 4060 FFMA 峰值（~105 TFLOPS）的 0.4%**。

新增 `ternary_ptq1_prefill_dp4a_kernel`（`ternary_rowsplit_prefill.cuh`）：每 CTA 覆盖 64 行 × 64 token
（每线程 8 行 × 4 token，128 线程），激活按 128 列组量化成 int8，一个 `dp4a` 覆盖 4 个权重×1 token，
替代每权重每 token 一次 FFMA；前 120 列走与解码 GEMV 相同的四列 quad 解码，qh 的 8 列保留 FFMA 链。
另加批量量化 kernel——**第一版没按 blockIdx 分配任务，8 倍冗余**，光这一项在 down 形状上就比 GEMM
本身还贵（138 ms vs 8.7 ms），修正后所有形状统一到 3.1–3.4 TMAC/s。

| 形状（T=302） | 参考 t8 | 批量 dp4a | 提升 |
|---|---|---|---|
| MLP gate_up（N=34816, K=5120） | 0.26 TMAC/s | **3.10** | ×11.7 |
| MLP down（N=5120, K=17408） | 0.28 | **3.42** | ×12.1 |
| attn/GDN（N=5120, K=5120） | 0.30 | **3.31** | ×11.0 |
| LM head（N=248320, K=5120） | 0.27 | **3.08** | ×11.4 |
| 同上但 T=9（serve 的实际粒度） | 0.15–0.19 | **1.8–2.3** | ×8.2–12.0 |

端到端：prefill **10.9 → 111–125 tok/s**；1541 token prompt **142.5 s → 13.4 s**；SSE 首 token
**2.10 s → 0.40 s**；decode 22.57 tok/s 不变。8192 上下文从"填满要约 12.6 分钟"变成"约 65 秒"。

两个必须记下的坑：

1. **serve 的 staged prefill 是按 T=9 调用线性层的**（诊断打印出来的，不是 1024），所以准入阈值必须
   放到 T ≥ 4，否则整条服务端预填充都留在参考 kernel 上——而 CLI 因为一次传整个 prompt（T=1157）
   会走新路径，造成"CLI 快了、serve 没快"的假象。
2. **scratch 的 scale 偏移与分配大小必须用同一个步进。** 曾经按实际 T 算分配、按固定步进 1024 取
   scale：T > 1024 时 scale 落进 xq 区间（把 int8 权重数据当 float 读，输出错但不崩），T 很小时
   越界踩内存（warmup 直接 illegal address）。现在统一按"最坏 K × 最坏 T"固定布局。

门禁：新增 `tools/verify/ternary_gemv/prefill_reference_check.cu`（12 组形状，含 token 数装不满 tile
的 37、行数不是 CTA 行块倍数的 67、单组 K、以及 qh tail 生效/清零两种），接进 `run_checks.sh`。
这个门禁不是形式主义：开发中真的踩到过 **qh 的 tail 在 token 循环里写成赋值而不是累加**，循环结束后
只剩最后一个 token 的 tail 值并被加到所有 token 上，端到端冒烟完全看不出来（文本仍连贯）。

*七、剩余空间与已排除方向*

- 引擎内实测（nsys，按形状）：gate_up（N=34816）约 **93 GB/s**、LM head（N=248320）约 103 GB/s。
  注意**微基准会偏乐观**：39 MB 的真实张量只有 L2 的 1.2 倍，迭代测量时部分命中缓存；引擎里
  每 token 读 5.93 GB 互不重叠的数据，是纯 DRAM。所以「内核还能快多少」要以引擎内数字为准。
- 非 GEMV 内核合计约 **6.5 ms/token**（激活量化 1.62 / rotation 2.09 / GDN 1.27 / rmsnorm 0.86 /
  memset 0.63），占当前 56.8 ms 的 11%。其中 rotation 每 token **8994 次启动**却只花 2.09 ms，
  激活量化 413 次启动花 1.62 ms——两者都是「小 kernel + 启动开销」形态，融合进上游 kernel
  （residual_add / rotation 的 epilogue）理论上能省下大部分，是目前唯一还有明确收益的方向。
- **测量噪声须知**：本机 SM 频率随电源状态在 1.68–2.01 GHz 摆动，内核又是部分指令受限的，
  **单次计时有约 ±20% 噪声**。所有带宽结论都应取多次试验的 median（`gemv_bandwidth.cu` 已内置）。
- **已证伪，不要重试**：
  - cp.async / shared memory staging（staged 70.7、staged2 69.4 GB/s）——瓶颈是发射率不是延迟隐藏。
  - 每 warp 处理 2 行以摊薄激活读取：bf16 下无差异，int8 下更差（78.3 vs 101.8，占用率下降）。
  - kernel 内重复量化激活：量化本身约 25 指令/组 vs 主循环 15，吃掉全部收益。
  - 激活预载进 shared 再算：与直接从 global 读无差异，排除「激活延迟」假设。
  - 两个 scale 平面预载进 shared：寄存器 40→30、占用率 48→64 warps，**带宽不变**。
  - 4 路累加器打断串行 FP 依赖链：**带宽不变**（编译器本就在打断）。
  - `__ldcs` 流式提示标记权重：134 → 110–123 GB/s，**更差**。
  - **权重重排为单平面交错布局：与三平面持平或更慢**（见 §9.1 五）。
