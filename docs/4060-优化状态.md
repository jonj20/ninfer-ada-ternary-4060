## 2. 预填充（prefill）

| | 之前 | 现在 | 提升 |
|---|---|---|---|
| 吞吐 | 10.9 tok/s（**与长度无关**，恒定） | **111 / 122 / 125 tok/s**（401/781/1541 tok） | **×11.5** |
| 1541 token prompt | 142.5 s | **13.4 s** | ×10.6 |
| SSE 首 token | 2.10 s | **0.40 s** | ×5.3 |
| 8192 上下文填满 | 约 12.6 分钟 | 约 65 秒 | ×11.6 |

**根因**：参考分块 GEMM 每 CTA 只做 1 个输出行 → 激活被重复读 rows 次（gate_up 每层约 108 GB
L2 流量），302 token × 27B 参数 = 1.63e13 FLOP 花了 28.1 s，即 **0.58 TFLOPS = FFMA 峰值的 0.4%**。

**形状实测（对参考 t8 内核）**：gate_up **×11.7**、MLP down **×12.1**、attn/GDN **×11.0**、
LM head **×11.4**（T=302）；T=9（serve 的实际调用粒度）**×8.2–12.0**。
绝对值统一在 **3.1–3.4 TMAC/s**（dp4a SIMT 峰值的 ~21%）。

### 2.1 tile 形状：小 T 的真正瓶颈是 CTA 数，不是算力

`Ptq1PrefillTile<R, TT, ROW_GROUPS, TOK_GROUPS>` 三个量绑定：
`kRowsPerCta = R*ROW_GROUPS`、`kTokensPerCta = TT*TOK_GROUPS`、`kThreads = ROW_GROUPS*TOK_GROUPS`，
而 `grid = (div_up(rows, kRowsPerCta), div_up(tokens, kTokensPerCta))`。两条实测结论：

1. **同一 `grid.x` 的各个 `grid.y` 会重读同一批权重行**，所以 `kTokensPerCta` 越大权重流量越大。
2. 在此前提下 **`kRowsPerCta` 越小 CTA 数越多**。旧的 T<16 配置 `kRowsPerCta=64`，n=17408 时
   只有 **80 个 CTA**，退化成延迟受限；而解码的 GEMV 约 **142 GB/s**。

当前分派（`ternary_rowsplit_gemm.cu` 的 `launch_ternary_gemm_t8`）与实测带宽：

| T | 配置 | MLP gate_up | MLP down | attn/GDN | LM head |
|---|---|---|---|---|---|
| 2 | `<1,1,16,2>` | 84.5 GB/s | 59.5 | 67.3 | **126.2** |
| 4 | `<1,1,16,4>` | 62.4 | 50.2 | 34.8 | 66.4 |
| 9 | `<8,4,8,4>` | 38.8 | **23.2** | **23.4** | 42.4 |
| ≥64 | `<8,4,8,16>` | 9.3 | 8.5 | 9.0 | 10.1 |

（换掉的旧配置在 T=2 只有 20~42 GB/s，在 T=4 只有 19~43 GB/s。复现：
`tools/verify/ternary_gemv/run_checks.sh tile`）

**T=16..63 曾经分派错了**：原来跳到 `<8,2,8,16>`（`kTokensPerCta=32`），在 T=16 白浪费一半槽位，
实测比 `<8,4,8,4>` **慢 70~124%**（T=32 慢 21~31%）。现已统一为 9..63 走 `<8,4,8,4>`——该配置在
T=9..64 整段都是最优或并列最优。

## 4.1 MTP 投机：修掉两个 bug 后从 2.41 到 22.66 tok/s

**结论：功能正常且已追平基线，但本卡上仍不划算，默认保持关闭。** 曾经的"慢一倍"是两个真 bug
叠加造成的假象，不是投机解码的固有代价。

| 配置 | 修之前 | 修门槛后 | 修 tile 后 | 每轮成本 |
|---|---|---|---|---|
| 基线（无 MTP） | 23.64 | — | **23.15** | 42 ms |
| draft=1 | 2.41 | 8.98 | **22.66** | 192 → **73 ms** |
| draft=2 | 3.01 | 10.26 | **17.59** | 201 → **118 ms** |
| draft=3 | 9.86 | 9.80 | **18.56** | 212 → **122 ms** |

**Bug 1：准入门槛把验证挡在快内核外面。** `ptq1_prefill_admits` 原来要求 `T >= 4`，而投机验证的
`T = draft + 1` 取 2..4。更要紧的是 `launch_ternary_gemm_t8` 里 T≥2 的两个后备
（`mma_admits`、`gemv_admits`）**都只认 PQ2_0**，PTQ1_0 落到最后一步 `launch_by_qtype<8>` 的
**参考平铺内核**——所以 draft=1/2 的 2.41 tok/s 是"未优化路径"的速度。改成 `T >= 2` 后 ×3.4~3.7。
（`T = 1` 走 `launch_ternary_gemm_t1`，根本不查这个谓词，所以 decode 不受影响。）

**Bug 2：小 T 的 tile 只有 80 个 CTA。** 见 §2.1。修完每轮 192 → 73 ms。

**剩下的瓶颈是接受率，不是实现**：draft=1 的 1.66 tok/round（接受率 66%）配 73 ms/轮，正好
等于基线的 23 tok/s——**打平而非超越**。要赢得靠更高的接受率（模型/蒸馏决定，调参改不动），
或者继续压每轮剩余的固定开销（MTP 头 3 次前向 + `gdn_replay_fold` + 每轮一次
`device.synchronize()`）。`--lm-head-draft` 另需 888 MiB 预留，只有约 702 MiB 可用，起不来。

- `tools/verify/ternary_gemv/prefill_reference_check`（**4 档 tile × 16 形状**）**PASS**

- 门禁抓到过端到端看不出来的 bug：qh tail 在 token 循环里写成赋值而非累加，循环结束后只剩最后
  一个 token 的 tail 值并被加到所有 token 上
- 只报数不判定的新工具：`prefill_tile_sweep`（tile 形状 / CTA 数 / 等效带宽）、
  `perf_probe.sh`（解码 / prefill / MTP 吞吐与每轮成本）、`kv_capacity_probe.sh`（KV 容量上限）

## 7. 已知问题

1. **间歇性 illegal address**（先前就存在，与本轮优化无关）：`gqa_attention_prefill.cu` /
   `l2norm.cu` 偶发 `cudaErrorIllegalAddress`，13 次里 2 次，随后 11 次未复现，出现在 T=9 预填充
   路径上。再遇到建议用 `compute-sanitizer` 抓一次。
2. **`/mnt/d` 9p 挂载不稳定**：`ls` 能列出文件但 `grep`/`stat` 打不开；曾有一次 edit 失败把
   `ternary_rowsplit_gemm.cu` 截断成 0 字节（已从 git 重放恢复），`tools/verify/ternary_gemv/`
   下的文件也被环境删过一次。**改动前先确认文件大小，重要改动后立刻提交。**
3. **测量噪声**：SM 频率随电源在 1.68–2.01 GHz 摆动，单次计时 **±20%**，带宽结论须取多次 median
   （`gemv_bandwidth.cu` 已内置 5 次）。
4. **`T >= 64` 的权重重读**：`kTokensPerCta` 固定 64，于是 T=128/256/1024 时 `grid.y` = 2/4/16，
   权重会重复读 2~16 次。**serve 的 staged prefill 是 9 token 一批，不在这条路径上**；受影响的是
   `--prefill-chunk 128/1024` 这类分块预填充。要修得让 `kTokensPerCta` 随 T 增长（模板实例化或
   换内核结构），不是一行分派能解决的。
5. **两个测量陷阱**（都已在 `perf_probe.sh` 里处理）：
   - **短 prompt 的 prefill 速率系统性偏低**：每请求固定开销被摊薄，13 token 只有 20~55 tok/s、
     600 token 约 110、1572/3132/4692 token 分别是 129/132/131。**横向比较必须带 token 数。**
   - **连续两次发内容完全相同的 prompt 会命中前缀缓存**，第二次 prefill 只要 0.10 s。照着这个做
     重复性测量会得出"波动 250%"的假象。
6. `ruff` / `mypy` 有 225 处既存报错，均在未触碰的 Python 侧。

## 8. 复现命令

```bash
# 正确性门禁（改完内核先跑）
NVCC=/usr/local/cuda-13.1/bin/nvcc tools/verify/ternary_gemv/run_checks.sh reference

# tile 形状扫描（改 launch_ternary_gemm_t8 的分派后复核；噪声大，必要时 --iters 20）
tools/verify/ternary_gemv/run_checks.sh tile

# 吞吐探针：解码 + MTP draft 0..3 + 长 prompt prefill，自动算每轮 ms
NINFER_BUILD_ROOT=<build> tools/verify/perf_probe.sh <artifact.ninfer> --drafts 0,1,2,3

# KV 容量上限
NINFER_BUILD_ROOT=<build> tools/verify/kv_capacity_probe.sh <artifact.ninfer>

# 起服务（默认 ctx 48000 / 输出不设限 / 非思考模式）
scripts/run-ternary-4060.sh
NINFER_CTX=32768 scripts/run-ternary-4060.sh      # 长对话更稳
NINFER_MODE=think scripts/run-ternary-4060.sh     # 思考模式 + 对应采样参数

# 端到端 A/B 开关
NINFER_TERNARY_PTQ1_RECURRENCE=0   # 退回每 lane 一个 trit 的解码内核（17.0 tok/s）
NINFER_TERNARY_PTQ1_PREFILL=0     # 退回参考分块 GEMM（prefill 10.9 tok/s）
NINFER_TERNARY_PTQ1_PREFILL_VERBOSE=1   # 报告 prefill 快路径为何没走上
NINFER_TERNARY_PTQ1_DP4A=0        # 退回 bf16 激活点积（13.2 tok/s）
NINFER_TERNARY_PTQ1_GEMV=0        # 退回 reference 解码（3.36 tok/s）
```
